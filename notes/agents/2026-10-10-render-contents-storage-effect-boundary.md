# Render-contents Storage effect boundary

- Unexpected hurdle: `render-contents` writes rendered HTML through a Storage bucket object captured by core, while the local GCP simulator constructs that same core directly.
- Diagnosis: the renderer needed a permission-first command adapter and a fresh capability for both Firestore trigger and authenticated HTTP invocations. The first full check exposed simulator composition that was not wired to the new adapter, followed by TSDoc type issues in the simulator adapter.
- Fix: move the Storage write behind `saveRenderedPage(permission, path, content, options)`, keep path-prefixing and rendered content decisions in core, inject the production Storage adapter at the cloud boundary, and provide an explicitly typed local simulator adapter. Tests verify fresh invocation capabilities and adapter forwarding.
- Evidence: focused Jest passed (4 suites, 69 tests), `npm run lint`, `npm run tsdoc:check`, and `npm run build:cloud` passed. Final `npm run check` passed all 10 gates; the test gate passed all suites and 100% coverage, duplication found 0 clones, audit found 0 vulnerabilities, and local E2E passed.
