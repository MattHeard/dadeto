# Process new page trigger write effects

- Unexpected hurdle: the existing batch facade accepted an invocation capability only at construction and captured it in returned closures; direct-page misses also still called `DocumentReference.update` in core. Both left write commands without an explicit permission parameter at the point of use.
- Diagnosis: traced every trigger path through skipped submissions, direct-page lookup, option/page creation, variant and author writes, stats updates, dirty resets, and batch commit. Query-only Firestore reads remain direct queries; every update/set/commit is now called through a facade method that requires the current invocation capability.
- Chosen fix: the raw Firestore batch remains in cloud and simulator adapters. The factory no longer accepts a capability, and each returned set/update/commit function takes AllowEffects as its first parameter without capturing it. Core passes the trigger capability to each command. The direct-page processed-marker path now uses the injected permission-first update adapter.
- Evidence: focused process-new-page Jest passed (3 suites / 41 tests); ESLint, JSDoc, and `npm run non-core-thin` passed; `npm run build:cloud` passed; configured elevated `npm run check` passed all 10 gates, including coverage, E2E, 0 clones, and 0 audit vulnerabilities. Full-check log: `/tmp/dadeto-process-new-page-check-final.log`.
- Next-time guidance: keep effect permission on each individual batch command and never bind a request token into a batch facade. Continue the lexicographic source-cloud audit at `src/cloud/process-new-story/index.js`.
