# Billing refund event matching

- Unexpected hurdle: `charge.refunded` carries a Charge aggregate, while Stripe identifies individual refund records through Refund objects. The charge may expose only its ten most recent refunds.
- Diagnosis: checked Stripe's event and refund API references, then traced the webhook allowlist, purchase-event inbox, refund-intent transaction, and existing reconciliation writer.
- Chosen fix: accept authenticated `refund.created` and `refund.updated` events; match their purchase, intent, Stripe PaymentIntent, Refund ID, USD amount, reservation, and remaining lot in one transaction before changing credits. Also inspect individual Refund records embedded in `charge.refunded`; retain charge aggregates without usable refund details for reconciliation.
- Quality evidence: focused billing/webhook coverage passed 87 tests with all five changed billing/auth/webhook modules at 100% branch coverage; targeted ESLint, TSDoc, whitespace, and duplication gates passed with zero clones. `DADETO_CHECK_TIMEOUT_MS=3600000 npm run check` passed all 10 gates, with 100% line, statement, function, and branch coverage and 11 local E2E tests passing. `npm run build:cloud` and generated billing/webhook `node --check` passed.
- Unexpected quality hurdle: the default 30-minute `npm run check` timeout expired after the test step had run 22 coverage shards; those shards showed 100% coverage but were not terminal evidence. The `DADETO_CHECK_TIMEOUT_MS` override raised the time limit without changing any gate and let the full suite finish.
- Next-time guidance: implement durable `received`/`deferred` replay as a separate bounded loop. The event receipt is already persisted and deferred receipts are retryable, but the worker that rescans deferred events after a state transition is still outstanding. Use a larger `DADETO_CHECK_TIMEOUT_MS` for aggregate checks on this test corpus.
