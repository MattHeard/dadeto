- Scope: resume the `assign-moderation-job` import review at `resolveFirestoreEnvironment` and `shouldUseCustomFirestoreDependencies`.
- Classification: `resolveFirestoreEnvironment` returns the supplied environment or invokes the injected environment getter; it does not issue a command effect. `shouldUseCustomFirestoreDependencies` checks optional override presence, function identity, and whether an environment override exists; it does not call the candidate Firebase functions or access the SDK.
- Call-tree check: app initialization, middleware registration, route registration, assignment persistence, and HTTP response sending are already invoked through permission-aware adapters and `AllowEffects` boundaries in `src/core/cloud/assign-moderation-job/index.js`. The request-time response and assignment paths each obtain permission through the runtime boundary; the startup token is used only during composition.
- Evidence: `test/cloud/assign-moderation-job/core.test.js` and `test/core/cloud/assign-moderation-job-core.coverage.additional.test.js` passed (2 suites, 69 tests). These cover environment override selection, getter invocation, custom Firebase dependency detection, and default behavior.
- Remaining hardening: core still names Firebase SDK `Firestore` and `DocumentReference` types in its composition contract. Although the actual `.set` is called only by the injected cloud adapter, the broad reference type leaves a future direct-write escape hatch visible in core. Next loop should move document-reference construction behind the cloud adapter and pass a UID plus assignment payload through the permission-aware write boundary, or prove a narrower opaque reference shape is sufficient. Do not mark this flow clean until that boundary is closed.
