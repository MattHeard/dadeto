# Billing expiry inbox atomicity

- Unexpected hurdle: webhook expiry processing persisted `received`, changed the purchase to `expired` in a transaction, and persisted `applied` only after that transaction returned. A process interruption in between left an unresolved inbox record after the state transition.
- Diagnosis path: followed `checkout.session.expired` from `src/core/cloud/payment-webhook/payment-webhook-core.js` into `markPurchaseExpired`; compared its transaction to the paid-purchase path, which already commits its event status with the purchase and credit mutation.
- Chosen fix: read the payment event in the expiry transaction and atomically set it to `applied` with the purchase transition. Preserve the verified event. Recover an already-expired purchase when its matching event is still `received`; persist ignored expiry outcomes. Add a webhook-level test that fails after the transaction, reconstructs the handler, retries the same event, and then delivers a late payment event.
- Evidence: `npx jest --runInBand --runTestsByPath test/core/cloud/billing/billing-runtime-core.test.js test/core/cloud/payment-webhook/expiry-restart.test.js` passed (2 suites / 40 tests); targeted ESLint passed; `npm run build:cloud` passed; `npm run check -- --skip-tests` passed 10/10 gates with zero clones. Full `npm run check` is not yet verified for this change; the serial coverage gate previously exceeded the command-session limit.
- Next-time guidance: keep the billing item Partial until a complete `npm run check` run finishes, then reconcile the remaining billing definition-of-done requirements: operation attempt identity, refund MVP/reconciliation, mandatory transitions, durable deferred processing and exact raw-body verification.
