# Atlas report read service retrospective

- **Unexpected hurdle:** The adapter-backed service could persist a validated whole-model report but had no read method for clients to retrieve it. The first focused run was blocked by sandbox `EPERM`; the elevated run then exposed a test-group line limit and that bundle import wraps a specific report-integrity error in the stable `invalid-accuracy-evaluations` category.
- **Diagnosis:** `createInterpretabilityResearchServiceV1` routes reads through `withBundle`, which passes the required permission token into `loadBundle` and imports/validates V2, V3, or V4 before returning data. V2/V3 imports normalize reports to an empty list, while V4 import rejects semantically tampered reports.
- **Chosen fix:** Added `readEvaluations(allowEffects)` to return the validated bundle's reports without writing. The report remains unchanged, including a synthetic mechanistic MSE that is worse than the sampling baseline. Tests cover permission forwarding, legacy empty results, and stable rejection of tampered summaries. Split report-read tests into their own `describe` block and assert the public import error category.
- **Evidence:** `npm run check:impact:run -- --files src/core/interpretability/researchService.js test/core/interpretability/researchEvaluationV4.test.js test/core/interpretability/researchServiceV1.test.js test/core/interpretability/testZodContract.test.js` passed 9 suites / 84 tests, with no uncovered lines or branches in changed-core `researchService.js`; ESLint, core-parse, and duplication passed (0 clones). `npm run check` passed all 10 fast local gates, selecting the same 9 suites / 84 tests; audit found 0 vulnerabilities.
- **Next-time guidance:** Keep report reads behind the same validated bundle loader and permission-token boundary as other research operations. The next integration slice should decide which report summaries the API/UI needs and preserve both positive and negative outcomes without triggering inference.
