# Object-minute rental search response effects

- Unexpected hurdle: the initial audit hypothesis treated the injected repository and GCS schedule provider as the entire core boundary; a deeper trace found HTTP response mutations inside the same core request path.
- Diagnosis: `executeSearchHttpRequest` directly set CORS headers and wrote JSON/status responses. The Firestore commitment repository and GCS schedule provider are read-only queries, but those query classifications did not cover the response effects.
- Fix: moved response writes behind permission-first adapters. The cloud function now wraps the internal handler in `createEffectHttpBoundary`; the local simulator binds a fresh permission through its injected `bindEffectBoundary`. The core receives only response adapters and explicitly forwards `AllowEffects` to header, status, and JSON operations.
- Evidence: focused search, cloud adapter, local simulator, and endpoint tests passed (5 suites, 74 tests); the changed simulator response adapter has 100% statements/branches/functions/lines; `npm run tsdoc:check`, scoped ESLint, `npm run build:cloud`, and elevated `TMPDIR=/home/matt/dadeto/.tmp npm run check` passed. The full check passed 10/10 gates, all 4 global coverage metrics at 100%, local E2E 11/11, 0 clones, and 0 audit vulnerabilities. Cloud build output includes the object-minute search effect adapter and updated request handler.
- Next-time guidance: when reviewing an endpoint, trace response helpers and error paths as well as injected SDK repositories; query-only dependencies do not imply that the whole request core is effect-free.
