# THREEFOLD pre-surge gate repair

- **Unexpected hurdle:** The gate-repair reducer, complete-run restore validator, and renderer all assumed repairs could only happen after the surge. Enabling the earlier route required preserving when the repair happened so its water outcome stayed distinct from late repair. The first aggregate check also found the renderer suite exceeded its 450-line function limit after adding a new case.
- **Diagnosis:** Traced the pawl interaction through `attemptThreefoldGateRepair`, `getThreefoldGateOutcome`, `restoreThreefoldSimulation`, and `getThreefoldToast`; the outcome suite already asserted that pre-surge repair was unavailable. The existing episode model had a reusable `gateRepaired` flag, but no timing marker.
- **Fix:** Added the optional `gateRepairedBeforeSurge` episode flag, serialized through the normalized episode state. Early repair restores the gate and keeps the drainage channel dry through surge, while late repair still leaves water through surge and recedes at aftermath. Ferry/passenger/Latchfolk outcomes remain governed by the existing crisis reducer. Moved the new renderer assertion into a dedicated test file to keep the established suite below its lint limit.
- **Next time:** When one interaction has different consequences by crisis phase, persist the phase distinction explicitly and test both save roundtrips. Keep the timed actor outcomes separate from the repaired structure's outcome. Run focused impact tests first, then `npm run build`, `npm run check`, and the exact-head hosted Full Check.
- **Evidence:** Focused impact tests passed (6 suites / 136 tests); `npm run build` passed; `npm run check` passed all 10 fast gates across five serial shards (960 suites / 6,629 tests, zero clones, zero audit vulnerabilities). Exact-head Full Check is pending.
