# Atlas held-out report summary integrity retrospective

- **Unexpected hurdle:** A schema-valid report could still carry MSE, accuracy-range, split, or compute values that disagreed with its 32 variant rows. Adding every check to the existing link validator also exceeded the local function-complexity limit.
- **Diagnosis:** Traced the report producer in `src/core/interpretability/algZooPilotHarness/index.js`: it requires a shared held-out split and matched compute, then derives overall/per-scale MSE, accuracy range, and material variation from variant values. Canonical sorting can change floating-point summation order slightly, so exact MSE equality would be too strict.
- **Chosen fix:** Recompute report aggregates at the V4 persistence boundary, require shared split and matched compute, and compare MSE values using a documented 1e-12 relative-or-absolute tolerance. Extracted provenance and summary validation into separate helpers to keep each function within lint limits. Added synthetic mutation cases for each summary field and preserved the worse-than-sampling result.
- **Evidence:** `npm run check:impact:run -- --files src/core/interpretability/index.js test/core/interpretability/researchEvaluationV4.test.js test/core/interpretability/testZodContract.test.js` passed (9 suites / 81 tests; ESLint, core-parse and duplication passed; changed-core `index.js` had no uncovered lines or branch arms). The final `npm run check` passed all 10 fast local gates, including the full serial Jest fallback selected by the unsupported Markdown change, with 0 duplication clones. An earlier check attempt hit `EAI_AGAIN` at the npm audit endpoint; its retry passed.
- **Next-time guidance:** Persistence validators should recompute derived research summaries from canonical raw rows before saving. Define a numeric tolerance from the producer's aggregation behavior, and test each independently mutable summary field. Split semantic validation helpers when coverage-driven hardening pushes a function over complexity limits.
